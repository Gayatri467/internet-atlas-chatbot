# internet-mapper-api — end-to-end PoC

One compose project that runs the whole chain: MRT dump → parquet → route state
→ Neo4j graph → HTTP API → browser UI. The individual PoCs are unchanged; this
directory orchestrates them and adds the serving layer.

```
                 ┌── stage1-mrt-decode  (../mrt-decode, Rust)
                 │      work/parsed_mrt.txt
                 ├── stage2-parquet     (../converter-parquet, pyarrow)
                 │      work/bgp_updates.parquet
                 ├── stage3-route-state (../route-state/app, DuckDB)
   MRT dump ─────┤      work/current_route_state.parquet + work/change_log.parquet
                 ├── stage4-as-graph    (../graph-poc/loader)
                 │      neo4j: (:AutonomousSystem)-[:ADJACENT_TO]->(:AutonomousSystem)
                 ├── stage5-prefix-graph (../prefix-graph/loader)
                 │      neo4j: (:AutonomousSystem)-[:ORIGINATES|SEEN_VIA]->(:Prefix)
                 └── stage6-enrich      (../enrich-graph/loader, live fetch)
                        neo4j: CAIDA relationship_type on :ADJACENT_TO
                               + PeeringDB name/org/country on :AutonomousSystem
                                        │
                          api ──────────┴── DuckDB reads work/*.parquet
                                            Neo4j over Bolt
```

Every stage shares `./work` as its handoff directory, so **nothing is copied
between PoC folders by hand**. `work/` is regenerated by the pipeline and
gitignored; it holds no source.

## Run it

```bash
make demo        # fetch + build + pipeline + up + walk every endpoint
```

That is the whole demo. It is idempotent — rerun it any time. Step by step:

```bash
make fetch       # download the sample MRT (skipped if ../mrt-decode/data/updates.gz exists)
make build       # api image + the five stage images
make pipeline    # stages 1-5, in order, each failing loudly
make up          # neo4j + api, waits for /health
make smoke       # assert every endpoint answers (and that 404s stay 404s)
make queries     # the cypher packs from graph-poc + prefix-graph
open http://localhost:12345/ui/
```

Individual stages: `make stage1` … `make stage6`. Teardown: `make clean`
(containers) or `make nuke` (containers, volumes, and `work/`).

Stage 6 enriches the graph from **CAIDA AS-relationships** and **PeeringDB**. It
adds no nodes: it tags `:ADJACENT_TO` edges with a CAIDA `relationship_type`
(`p2c`/`p2p`) + `relationship_source`, and sets PeeringDB `name`, `organization`,
`country` and network classification on `:AutonomousSystem` nodes. It only keeps
external records that touch ASNs already in the graph, and is idempotent, so a
small MRT sample yields only a handful of matches — a bigger sample enriches
more. Surface it at `GET /api/v1/asn/{asn}` (identity) and on
`GET /api/v1/asn/{asn}/neighbors` (relationship per pair).

Like the MRT sample, the raw source files are **cached locally** in
`./enrich-graph/input` (the CAIDA `*.as-rel2.txt.bz2` and PeeringDB
`peeringdb_net.json` / `peeringdb_org.json`). The stage reaches the network only
on the first run or when a cached file is missing; every rerun reads the local
copies, so it is fast and works offline once populated. Force a fresh download
with `FORCE_REFRESH=true make stage6`, or clear the cache by deleting those
files. Skip a source entirely with `SKIP_CAIDA=true SKIP_PEERINGDB=true make
stage6` (e.g. offline with no cache yet). `make nuke` leaves the cache in place,
same as it does for the MRT sample.

If the stage-6 **container** has no outbound network (some sandboxes block it),
pre-seed the cache from the host with **`make fetch-enrich`** — the same
download-if-missing pattern as `make fetch`, but for CAIDA + PeeringDB. It is a
prerequisite of `make demo`, so the default flow works with or without container
egress.

Budget **~12 minutes** for a clean `make demo` on a busy machine — most of it is
the Rust and cgo image builds plus two cold Neo4j starts. Reruns are far
quicker.

If a run is interrupted (Ctrl-C, closed terminal), `docker compose run` leaves
its stage container alive, and a live stage 3 keeps the route-state DuckDB file
locked. The next run then fails with
`Could not set lock on file "/state/route_state.db": Conflicting lock is held in
PID 0` — DuckDB says PID 0 because the holder lives in another PID namespace.
`make guard` (a prerequisite of every stage) catches this and tells you to run:

```bash
make unlock      # clear stage containers left behind by an interrupted run
```

### Knobs

| Variable | Default | Effect |
|---|---|---|
| `MRT_LIMIT` | `100` | records parsed from the MRT dump |
| `MRT_SOURCE` | `/mrt/updates.gz` | local path **or** an https URL — the Rust parser takes either |
| `COLLECTOR` | `route-views4` | collector name stamped into the parquet |
| `RESET_STATE` | `false` | `true` discards the incremental route-state DB first |
| `MRT_URL` | RIPE rrc00 2026-01-31 23:00 | what `make fetch` downloads |
| `FORCE_REFRESH` | `false` | `true` re-downloads stage 6 sources even if cached in `enrich-graph/input` |
| `CAIDA_FILE_URL` | *(auto)* | pin a specific serial-2 file; empty auto-discovers the newest |
| `PEERINGDB_API_KEY` | *(none)* | optional PeeringDB API key for higher rate limits |
| `SKIP_CAIDA` / `SKIP_PEERINGDB` | `false` | skip one source in stage 6 (e.g. when offline) |

`make pipeline` is incremental by design: stage 3 keeps its DuckDB state in a
named volume and skips events it has already processed, so a second pass over
the same input produces no new changes. Use `make reset-pipeline` for a clean
single pass — that is what makes `change_log.parquet` reflect exactly one run.

A bigger sample gives a much better demo (multi-origin prefixes and origin
changes are rare in 100 records):

```bash
MRT_LIMIT=50000 make reset-pipeline && make reload
```

## Querying the two stores directly

[`docs/OPERATIONS.md`](docs/OPERATIONS.md) is the query reference: the Neo4j data
model and its read/write/maintenance operations, what to try from DuckDB against
the three parquet files, and which store answers which question. Every query in
it was run against a live stack and shows real output — including the SQL that
derives the same 279 adjacency edges Neo4j holds, which doubles as a
cross-store consistency check.

## Endpoints

`GET /openapi.yaml` is the full spec; `GET /ui/` is the bundled explorer.
Prefixes are URL-encoded in paths (`8.8.8.0%2F24`).

| Endpoint | Store |
|---|---|
| `/health` | both, plus which parquet files are bound |
| `/api/v1/stats`, `/api/v1/snapshot` | DuckDB + Neo4j counts |
| `/api/v1/examples` | a prefix and ASN that exist in the loaded data |
| `/api/v1/prefix/{p}` | DuckDB summary **joined with** Neo4j origins |
| `/api/v1/prefix/{p}/paths`, `/history` | DuckDB |
| `/api/v1/asn/{asn}/neighbors`, `/prefixes` | Neo4j |
| `/api/v1/graph/neighborhood/{asn}` | Neo4j — `{nodes, edges}` for rendering |
| `/api/v1/analytics/top-origins`, `/collectors`, `/unstable-prefixes` | DuckDB |
| `/api/v1/analytics/hotspots` | **DuckDB churn × Neo4j topology** |
| `/api/v1/multi-origin-prefixes` | Neo4j |
| `POST /api/v1/admin/reload` | rebind the parquet views without a restart |

`/api/v1/analytics/hotspots` is the endpoint that justifies running both stores:
DuckDB's change log ranks prefixes by how much they moved and whether they are
still live, and Neo4j says who announces them and how well connected those
origins are. In the sample data it surfaces `84.205.80.0/24` — 14 changes, 7
withdrawals, `currently_live: false`, no origin left in the graph.

Nothing hard-codes a prefix or ASN: `/api/v1/examples` feeds the demo script,
the smoke test and the UI, so all three work on any MRT sample.

## The UI

`/ui/` is one self-contained HTML file (no CDN, no build step) served from
`web/`. Stat tiles from `/stats`, a force-directed view of
`/graph/neighborhood`, the churn hotspot table, and a details panel. AS nodes
are blue circles sized by degree, prefixes are orange squares; solid edges are
`ADJACENT_TO`, dashed are `ORIGINATES`. Drag to move, scroll to zoom, click for
detail, **Table** for the same subgraph as rows. Light and dark are both
styled.

## Local development

```bash
DOCS_DIR=./docs WEB_DIR=./web \
CURRENT_STATE_PARQUET=./work/current_route_state.parquet \
CHANGE_LOG_PARQUET=./work/change_log.parquet \
NEO4J_URI=neo4j://localhost:7687 \

```

Config is all environment (`internal/config`); the defaults are the container
paths.

## Notes

- **`data/` is superseded by `work/`** and no longer mounted. Safe to delete.
- **`../graph/graph-compose.yaml` is superseded by this compose file.** Both
  define a Neo4j on 7474/7687, so they cannot run at once — bring that one down
  (`docker compose -f ../graph/graph-compose.yaml down`) before `make up`.
- Prefix routes need gin's raw-path matching (`UseRawPath`), otherwise `%2F`
  decodes to a path separator and the router 404s before any handler runs. See
  `internal/httpapi/router.go`.
- DuckDB `LIST` columns (`as_path`, origin lists) must be scanned into `any` and
  converted — `to_json(...)` into a `string` fails at the driver. See
  `intList` in `internal/store/duckdb.go`.
- Neo4j holds no persistent truth here: stages 4 and 5 rebuild it from the
  parquet files with `MERGE`, so dropping the volume costs one `make pipeline`.
- The Neo4j healthcheck probes with `cypher-shell`, not `wget`. Port 7474 starts
  listening before the `neo4j` *database* is queryable, so an HTTP-only check
  reports healthy while the loader stages still die with
  `Neo.TransientError.General.DatabaseUnavailable`.
- `route-state/app/reconstruct.py` replays its batch inside one transaction.
  Without it DuckDB auto-commits (and WAL-flushes) every statement in the loop —
  100 events took 4m52s that way versus roughly ten seconds now, and any larger
  `MRT_LIMIT` was simply not viable.
- Both graph loaders now `CALL db.awaitIndexes(300)` after creating their
  constraints, and the AS loader retries `TransientError` batches. Without the
  await, a clean load races the constraint's background index population and
  dies with `Neo.TransientError.Transaction.DeadlockDetected` — a coin flip that
  only reproduces when the Neo4j volume is empty, i.e. the clean-demo path.
